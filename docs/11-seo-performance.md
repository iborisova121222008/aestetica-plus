# SEO and Performance

## 1. Purpose

This document defines technical SEO, local SEO, image discoverability, rendering, caching, and performance requirements for Estetica Plus.

Primary market:

```text
Bulgaria
```

Locales:

```text
Bulgarian: /bg/...
English:   /en/...
```

SEO is built into the content model and application architecture. It is not a launch-week plugin or a guarantee of ranking.

## 2. Goals

- make every approved public page crawlable and understandable;
- serve useful BG and EN locale variants;
- support local discovery for the studio;
- provide accurate metadata and structured data;
- make image-heavy pages fast on mobile;
- achieve strong real-user Core Web Vitals;
- avoid duplicate, thin, draft, and private indexable pages;
- give editors safe SEO controls;
- measure organic performance after launch.

## 3. Indexable Page Types

Initial indexable pages:

- BG and EN homepage;
- service sections and categories with meaningful content;
- individual published service pages;
- gallery/portfolio pages with sufficient context;
- about page;
- contact/location page;
- approved informational/blog pages when introduced;
- required public policy pages where appropriate.

Normally not indexable:

- admin panel;
- customer portal;
- login, registration, reset-password, and verification pages;
- booking steps and confirmation pages;
- internal search/filter combinations;
- previews and drafts;
- API routes;
- empty translation placeholders;
- private appointment or media URLs.

## 4. URL Strategy

Canonical locale routes:

```text
https://esteticaplus.bg/bg/...
https://esteticaplus.bg/en/...
```

Rules:

- use lowercase stable slugs;
- use localized slugs where approved;
- keep one canonical URL per locale page;
- avoid IDs and query strings in canonical editorial URLs;
- do not index filter/sort/pagination variants unnecessarily;
- redirect one canonical hostname consistently;
- use permanent redirects for approved permanent slug changes;
- avoid redirect chains;
- retain redirect records for renamed published services.

The root `/` redirects to the approved default locale behavior. It is not a third duplicate homepage.

## 5. Localized URLs and Hreflang

Every paired BG/EN page provides:

```text
hreflang="bg"
hreflang="en"
hreflang="x-default" when the root/default behavior warrants it
```

Rules:

- each locale version references itself and the other published variants;
- reciprocal links are consistent;
- an unpublished/missing EN page is not advertised as an alternate;
- canonical points to the current locale URL, not always to Bulgarian;
- alternates use absolute production URLs;
- the HTML `lang` attribute matches the visible page language;
- sitemap alternates and page metadata use the same mapping.

Do not automatically expose incomplete machine-like EN pages only to create hreflang pairs.

## 6. Metadata

Every indexable page provides:

```text
title
description
canonical
language alternates
Open Graph title
Open Graph description
Open Graph URL
Open Graph image
robots directive
```

Metadata is produced by Next.js server metadata APIs from approved content.

It is not generated by a client-side effect.

## 7. Title Rules

Direction:

```text
Primary page topic | Estetica Plus
```

Examples:

```text
Почистване на лице в София | Estetica Plus
Facial Treatments in Sofia | Estetica Plus
```

Rules:

- describe the actual page;
- keep the most important topic early;
- avoid repeating the same title across services;
- avoid unnatural keyword lists;
- use the brand once;
- allow reviewed per-locale override in admin;
- provide a sensible generated fallback from localized content.

Exact display length is not enforced as a character myth. Preview likely truncation and prioritize meaning.

## 8. Description Rules

- summarize the page accurately;
- write independently in BG and EN;
- use natural language and a useful reason to visit;
- avoid unsupported claims;
- avoid identical descriptions across many services;
- do not stuff locations or keywords;
- allow reviewed admin overrides;
- fall back to an approved short description when no override exists.

A metadata description can influence the snippet but does not guarantee Google will use it.

## 9. Open Graph and Social Metadata

Public pages define:

- localized social title and description;
- canonical page URL;
- appropriate locale;
- approved social image;
- image dimensions and alt where supported;
- site/brand name.

Use a dedicated Cloudinary `seoSocial` transformation preset.

The homepage hero is not automatically used if its crop does not work for social sharing.

Draft, private, and temporary placeholder images must not become production social images.

## 10. Robots

Production `robots.txt`:

- permits crawling of intended public content;
- references the canonical sitemap;
- avoids pretending that `Disallow` protects private information.

Private areas use real authentication and appropriate `noindex` behavior.

Non-production environments:

- require access restriction where possible;
- return `noindex`;
- do not reuse production canonical URLs in a way that creates indexing confusion.

Do not block CSS, JavaScript, images, or structured-data pages needed for rendering unless there is a specific reason.

## 11. XML Sitemap

The sitemap contains only canonical, indexable, published URLs.

Include:

- each published BG URL;
- each published EN URL;
- accurate locale alternates;
- meaningful `lastmod` derived from content changes.

Exclude:

- drafts;
- archives not meant for public discovery;
- admin/customer routes;
- booking flow states;
- redirecting URLs;
- error pages;
- arbitrary search/filter URLs.

If URL volume grows, use a sitemap index and split by stable content type or size.

The sitemap is generated from authoritative published data, not a manually maintained list.

## 12. Structured Data Strategy

Use JSON-LD generated on the server.

Potential types:

```text
Organization
LocalBusiness or the most accurate supported subtype
WebSite
WebPage
BreadcrumbList
Service
FAQPage only when current Google eligibility and visible content justify it
```

Rules:

- select the most accurate valid type;
- data must match visible page content;
- do not mark up hidden or invented reviews, prices, services, or claims;
- use stable canonical `@id` values;
- connect organization/business, webpage, service, and breadcrumb entities consistently;
- validate output before launch and after major template changes;
- structured data can improve understanding but does not guarantee rich results.

## 13. Local Business Data

The contact/location page and site-wide entity provide consistent:

```text
business name
canonical URL
logo
telephone
address
geo coordinates when verified
opening hours
sameAs social profiles
image
price range only when meaningful and accurate
```

Before publication, confirm:

- official legal/display business name;
- exact public address;
- public phone;
- accepted appointment/contact channels;
- final opening hours;
- map coordinates;
- logo and representative image;
- social URLs.

Website, Google Business Profile, social profiles, and important directories should use consistent business information.

Do not publish private personal contact details as business data.

## 14. Service Structured Data

Published service pages may describe:

- service name;
- description;
- provider/business;
- area served;
- image;
- URL;
- offer/price information only when accurately representable.

Price semantics must remain honest:

- `FIXED` may expose one exact current price;
- `FROM` must not be represented as a guaranteed fixed price;
- `RANGE` requires correct range meaning;
- `PER_AREA` and `PER_ITEM` require visible context;
- `CONSULTATION_REQUIRED` must not invent a number.

Structured data uses the same authoritative service model as the visible page.

## 15. Reviews and Ratings

Only approved public reviews appear.

Rules:

- do not generate fake reviews;
- do not mark up hidden reviews;
- do not change customer meaning;
- do not assume self-serving business review markup will produce star rich results;
- ensure any aggregate value is mathematically derived from eligible visible reviews;
- update/remove markup when reviews are unpublished;
- validate against current Google guidelines before enabling review-related structured data.

## 16. Breadcrumbs

Service hierarchy:

```text
Home
→ Section
→ Category
→ Service
```

Breadcrumbs:

- use localized visible labels and URLs;
- match page hierarchy;
- provide accessible navigation;
- use `BreadcrumbList` JSON-LD where valid;
- omit misleading empty levels.

## 17. Content Quality

Each service page should provide genuinely useful, reviewed content such as:

- what the treatment is;
- expected purpose and benefits without guarantees;
- who it may be suitable for;
- treatment process;
- duration;
- transparent price presentation;
- preparation and aftercare;
- contraindication/recovery information where professionally approved;
- authentic imagery;
- clear booking action;
- location/contact context.

Avoid:

- near-duplicate pages differing only by one keyword;
- automatically generated filler;
- copied competitor text;
- unsupported medical or permanent-result claims;
- invisible keyword blocks;
- doorway pages for locations not served.

Professional treatment and safety content must be reviewed by an appropriate qualified person.

## 18. BG and EN Content

Bulgarian is the primary editorial locale.

English pages:

- receive intentional human-reviewed translation;
- use natural English terminology;
- preserve the same factual meaning;
- may remain draft until complete;
- do not inherit Bulgarian title/description silently;
- use locale-appropriate currency/date presentation while preserving authoritative values.

Translation status is visible in admin.

Detailed localization rules belong in `docs/12-internationalization.md`.

## 19. Image SEO

Requirements:

- meaningful localized alt text;
- relevant image near relevant text;
- stable crawlable CDN delivery for public images;
- descriptive internal asset organization;
- width and height/aspect ratio;
- responsive transformed sizes;
- approved captions where useful;
- indexable Open Graph/structured-data image URLs;
- no private or draft image in public markup.

Before-and-after content:

- has confirmed consent;
- is clearly labelled;
- avoids misleading enhancement;
- includes context rather than being an unexplained image-only page.

Do not use alt text as a keyword list.

## 20. Rendering Strategy

Public marketing and service pages are server-first.

Use:

- React Server Components by default;
- static generation or controlled revalidation for stable published content;
- dynamic rendering only when data genuinely requires it;
- client components only for interaction;
- server-generated metadata and JSON-LD.

Avoid:

- client-only empty shells for indexable content;
- rendering titles/descriptions after hydration;
- hiding core text behind interactions;
- infinite-scroll-only discovery without crawlable navigation;
- requiring login/cookies for public service content.

## 21. Caching and Revalidation

Public content may use caching and on-demand revalidation.

After an approved admin mutation:

- service publication revalidates its page and relevant listings;
- category changes revalidate affected hierarchy;
- hero changes revalidate locale homepage;
- review changes revalidate visible review consumers;
- slug changes create redirects and revalidate old/new paths.

Dynamic booking availability:

- is not treated as static SEO content;
- is always revalidated authoritatively on booking;
- is excluded from general long-lived page caching.

## 22. Core Web Vitals

Targets use Google’s current “good” thresholds at the 75th percentile where applicable:

```text
LCP: ≤ 2.5 seconds
INP: ≤ 200 milliseconds
CLS: ≤ 0.1
```

Measure separately for mobile and desktop and prioritize real-user field data.

Lab tools support diagnosis but do not replace field measurement.

## 23. Largest Contentful Paint

Likely homepage LCP:

```text
hero image or hero text block
```

Requirements:

- server-render hero content;
- load the actual hero image with high priority;
- provide correct responsive `sizes`;
- use Cloudinary `f_auto` and `q_auto`;
- request the correct width;
- avoid loading both full desktop and mobile images;
- avoid a heavy client-only hero carousel;
- keep overlays CSS-light;
- optimize fonts needed above the fold;
- keep initial server response and API content fetch efficient.

Do not lazy-load the true LCP image.

## 24. Interaction to Next Paint

- keep public pages server-first;
- ship only necessary client JavaScript;
- load Framer Motion only in interactive/animated boundaries;
- avoid large client state providers around the whole site;
- debounce non-critical inputs;
- split admin/calendar/media code from public bundles;
- keep event handlers short;
- avoid hydration work for static service content;
- use progressive enhancement where practical.

On mobile, animation never takes priority over input responsiveness.

## 25. Cumulative Layout Shift

- reserve image dimensions/aspect ratios;
- use stable hero height with mobile browser controls considered;
- preload/use optimized fonts without destructive swaps;
- reserve error/message space where practical;
- avoid inserting banners above visible content unexpectedly;
- ensure skeletons match final dimensions;
- do not resize buttons or cards on hydration;
- test cookie/consent UI impact.

## 26. Images and Galleries

- Cloudinary serves transformed CDN assets;
- load only visible gallery thumbnails initially;
- paginate or incrementally reveal large collections;
- use small thumbnails in grids;
- load detail image only when opened;
- avoid eager-loading before/after comparisons below the fold;
- provide stable placeholders;
- prefetching must not download complete galleries;
- monitor Cloudinary transformation usage.

The VPS does not serve original gallery files.

## 27. Fonts

- use approved licensed font sources;
- self-host or use a privacy/performance-appropriate optimized loading strategy;
- limit families, styles, and weights;
- subset to required character coverage including Cyrillic and Latin;
- verify Bulgarian Cyrillic quality;
- preload only fonts needed above the fold;
- define fallbacks with similar metrics;
- use `font-display` behavior that does not hide text for long periods.

Final typefaces are validated for both BG and EN before implementation is locked.

## 28. CSS and JavaScript

- Tailwind output contains only used utilities;
- design tokens remain centralized;
- avoid large global CSS and duplicated component styles;
- use Client Components only where needed;
- dynamically load heavy admin-only components;
- do not include booking/admin libraries in normal public page bundles;
- inspect bundle size after major dependencies;
- avoid third-party scripts by default;
- load analytics/marketing scripts with an intentional consent and performance strategy.

## 29. API and Database Performance

Public content endpoints:

- return only necessary fields;
- use indexed slug/locale/publication queries;
- avoid N+1 service/category/media reads;
- cache stable published output deliberately;
- paginate large galleries and lists.

Booking endpoints:

- remain dynamic;
- use indexed resource/time queries;
- return bounded date ranges;
- avoid exposing entire staff schedules;
- recheck availability transactionally.

Slow-query monitoring belongs in `docs/15-observability.md`.

## 30. Performance Budgets

Initial budgets are enforced per route type and refined with real content.

Direction:

- no unoptimized original in public slots;
- minimal first-load client JavaScript on marketing/service pages;
- no public-page dependency on admin/calendar bundles;
- no render-blocking third-party marketing script without approval;
- stable dimensions for all prominent media;
- representative mobile test before merging a major visual feature.

Concrete JavaScript and image byte budgets are set during the first implemented pages, when the selected fonts and real hero photography are available.

## 31. Accessibility and SEO

SEO must not compromise accessibility.

Requirements:

- one clear page-level heading;
- logical heading hierarchy;
- semantic links/buttons;
- descriptive link text;
- visible keyboard focus;
- meaningful localized alt;
- accessible menus and dialogs;
- skip link;
- content available without motion;
- sufficient contrast over imagery;
- form labels and validation.

Search-engine crawlability is not a substitute for a usable page.

## 32. Redirects and Removed Content

- permanent slug changes use permanent redirects;
- redirect target is the closest useful equivalent;
- avoid redirecting every removed service to the homepage;
- archived service with no replacement may return a deliberate not-found/gone strategy;
- preserve high-value historical URLs where content has a valid successor;
- track redirect chains and loops;
- update internal links and sitemap after URL changes.

## 33. Error Pages

Provide localized:

- not found;
- unexpected error;
- temporary unavailable state.

Error pages:

- do not expose stack traces;
- provide navigation to useful public content;
- return correct HTTP status;
- are lightweight;
- do not masquerade as successful indexable content.

## 34. Analytics and Search Tools

Before adding analytics:

- define actual questions and events;
- review privacy/consent requirements;
- minimize collected personal data;
- avoid transmitting booking form content;
- assess script performance.

Launch setup:

- Google Search Console property;
- sitemap submission;
- Bing Webmaster Tools if useful;
- privacy-approved analytics;
- real-user Web Vitals reporting;
- conversion events such as booking-start and confirmed booking without sensitive details.

## 35. Search Console Workflow

After launch:

1. verify canonical domain property;
2. submit sitemap;
3. inspect representative BG and EN URLs;
4. verify rendered content and canonical/hreflang;
5. monitor indexing and enhancement reports;
6. monitor Core Web Vitals;
7. review crawl errors and redirects;
8. compare queries/pages by locale;
9. investigate changes rather than reacting to single-day noise.

## 36. Testing

### Automated

- unique localized title/description where required;
- canonical host and locale;
- reciprocal hreflang;
- robots rules by environment;
- sitemap contains only published canonical URLs;
- no admin/customer/preview URLs in sitemap;
- valid JSON-LD serialization;
- image dimensions and alt handling;
- noindex on protected routes;
- redirect tests.

### Manual

- Google Rich Results Test where applicable;
- URL Inspection after launch;
- mobile and desktop Lighthouse diagnosis;
- keyboard/accessibility audit;
- Open Graph preview;
- real device/network tests;
- rendered HTML review with JavaScript constraints;
- representative BG Cyrillic and EN typography.

### Field

- Core Web Vitals at 75th percentile;
- route-type breakdown;
- mobile/desktop separation;
- image/CDN errors;
- organic landing-page engagement and booking conversions.

## 37. Launch Checklist

- one canonical hostname;
- valid HTTPS;
- `/bg` and `/en` strategy works;
- root redirect is intentional;
- unique required metadata;
- canonical and hreflang validated;
- sitemap and robots available;
- draft/admin/customer routes excluded;
- LocalBusiness data matches visible verified business details;
- structured data passes validation and content guidelines;
- final logo/social images configured;
- production hero optimized;
- no temporary competitor/reference imagery;
- published meaningful images have appropriate alt;
- redirects tested;
- 404 returns correct status;
- mobile LCP/INP/CLS tested;
- Search Console configured;
- privacy-approved analytics only;
- real-user monitoring enabled.

## 38. Acceptance Criteria

- indexable BG and EN pages are rendered with useful HTML;
- each published locale page has correct self-canonical and alternates;
- sitemap contains only canonical published URLs;
- private and workflow pages are not indexable;
- metadata uses approved localized content;
- structured data matches visible facts;
- public images are responsive Cloudinary variants;
- homepage does not download two full hero variants;
- no layout shift from prominent images;
- public service pages avoid unnecessary client JavaScript;
- current good Core Web Vitals thresholds are targeted and measured;
- SEO configuration can be managed safely without arbitrary code;
- ranking, reviews, and treatment outcomes are never represented misleadingly.
